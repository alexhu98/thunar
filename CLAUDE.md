# Thunar (alexhu98 fork)

## Branches and PRs
- Work on a branch named `<issue>-<short-slug>` and open the PR into `main`, the default branch. Put `Closes #<issue>` in the PR description, or `Refs #<issue>` when the PR does only part of the issue.
- In a cloud session, ignore the `claude/…` branch the session is assigned. Once the issue is known, create `<issue>-<short-slug>` from `origin/main`, and push and open the PR from it.
- Never push to the `upstream` remote. Never touch `master` or `xfce-4.20`: they mirror upstream.
- The agent squash-merges a PR it opened, titled `<PR title> (#<issue>…) (#<pr>)`, once all of these hold on its head commit, with CI run on top of the current `main` (when `main` has moved since, the agent updates the branch and waits for the new run): build, verify, explainer, review and summary are green, and review-report is green or skipped because review wrote its own report with no fix to push; explainer ran its steps rather than skipping them, and so did build and verify unless both ran `No code changed` instead; review reviewed the head, or skipped it because an earlier head of the PR was reviewed and only `explainers/` changed since, or because the head is CI's own fix commit from that review; every review finding is fixed, resolved or accepted under the CI review rules below, none closed by a `Review-accept` the agent added outside them; the latest `/visual-verify` verdict is PASS, or build and verify ran `No code changed`, so there are no shots to audit; no comment from the owner is unanswered; the narration is stamped.
- The agent doesn't merge, and asks the owner instead, when a finding needs a decision, `/visual-verify` is FAIL or INCONCLUSIVE, CI fails twice on the same thing after a fix, or the change behaves differently from what its issue assumed. The owner merges those PRs, upstream-merge PRs (#30) and PRs the agent didn't open.
- After opening a PR or pushing to one, watch it without asking (subscribe to its activity where the session can), and act on its CI results and reviews, except while a question waits for the owner (see "Working with the owner").

## Working with the owner
- When a turn is blocked on the owner or its next step needs them, end it with a short multiple-choice "**What I need from you**" section they can answer with one number or letter, once per question (see below). Otherwise omit it entirely, with no "Nothing needed from you" line.
  - One decision: numbered options; the owner replies with the number. "1. Fix the tile check (recommended) 2. Leave it as is" → "1".
  - Several independent decisions: numbered decisions, lettered options. "1. Tile padding: A. 12px (recommended) B. Keep 8px  2. Bar color: A. Blue (recommended) B. Grey" → "1A 2B". A bare number means that decision's recommended option.
  - Each option: one concrete outcome, at most 20 words; recommended first and marked.
  - An action only the owner can do: the exact what and where, plus a one-key reply like "1. Done".
  - Several items: quickest or most blocking first; say what you'll get on with meanwhile.
- Standard SOP (reviewing the diff, staging, committing, pushing, opening the PR, merging one that passes the merge rule above) never needs the owner's attention, so it is never an option, an attention item or a closing prompt. A turn with only SOP left isn't blocked on the owner.
- Never bury a request for the owner in the middle of a long update.
- Don't post a message for a routine event: a CI comment edited, a check still running, an event for an older head, or an echo of the agent's own post. Read it and end the turn with one short line at most (an empty turn makes the harness ask for a reply), without repeating "What I need from you". Post only for a result (pass or fail), a blocker, a merge or a new question.
- Ask a pending question once. Repeat it only when the owner asks.
- While a question waits for the owner in an interactive session, unsubscribe from the PR's activity and schedule one `send_later` check-in instead, so a CI result or the owner's answer isn't missed, then subscribe again once the owner has answered. On the check-in, act only on a result or the owner's answer. An interactive session is any session where the owner answers in its chat, batch group sessions included.
- When asked what a term means ("what is X?", "explain X"), answer in 20 words or fewer per item: one sentence each, no preamble, no worked example. If it genuinely needs more, give the short version first and offer to expand.
- When a turn ends a long task or the answer runs past a screen, open with what was done or found (one line), then anything you're unsure of (one line; omit it if nothing is). Details go below; "What I need from you" stays at the end.
- When `/code-review --fix` finishes, list the skipped findings as S1, S2, …, each with a one-line reason it was skipped and the fix you recommend. Never use plain bullets for them.
- When you find a change the current issue doesn't cover (another feature or fix, docs, `CLAUDE.md`, CI, skills), don't add it to this PR and don't start it here. Offer only "Open an issue". The issue gets what you found (approach, prior-art files, risks, test approach), and a new web session implements it.

## Fixes
- Prefer the simplest fix that matches an existing pattern in the codebase. Search for prior art before introducing a new mechanism (new instances, isolation layers, new architecture).
- For a UI bug that affects several dialogs or views, prefer a general fix in the shared widget or code path over per-dialog patches, and propose the shared fix first.

## Building
- Build from git with `--enable-maintainer-mode`, as `debian/rules` does: `sudo add-apt-repository -y ppa:zorinos/stable` (Xfce 4.20 libraries), `sudo apt-get build-dep -y ./`, then `dpkg-buildpackage -b -us -uc`.
- Never build from the release tarball. Its pre-generated gdbus files need GLib 2.84, and Ubuntu 24.04 (noble) has 2.80. A git build regenerates them.
- Never run `apt-get update` limited to one source list (`-o Dir::Etc::sourcelist=…`). It deletes the other sources' package lists, so the next install finds nothing from noble.

## Verify
- Every feature PR adds `verify/<issue>.sh`, and its description has a `# | Shot | Proves` table of what each screenshot proves: one row per pair or single shot, `#` being CI's shot number linked as `[6](#shot-6)`.
- CI's `verify` job runs after the build on every PR. On a PR that changes only `explainers/`, `.claude/`, `*.md` or narration files (outside `debian/`, `verify/` and the root `README.md`), build and verify skip their steps and run `No code changed` instead, and the summary says so. Otherwise it installs the built `thunar`, `thunar-data` and `libthunarx-3-0` debs, then runs the smoke test (Thunar is still running 10 s after launch) and each `verify/<issue>.sh`, each under its own Xvfb. It numbers the shots (a pair is one number, the smoke test's last), makes each pair one 1920 px before/after image, and commits the screenshots and those images to the orphan `shots` branch under `pr-<n>/`. CI keeps four PR comments, in this order: the summary (checks, the key before/after pair, the shots table), the code review (with every finding the PR has had), verify (results and every other shot, each pair under its Action, Proves, Before and After) and the explainer. Nothing in them is collapsed. Those comments are CI's proof, not the agent's report.
- A `verify/<issue>.sh` runs from the repo root with `bash`, with its own Xvfb, xfwm4 and D-Bus session, a fresh `HOME` and its own XDG folders, for at most 120 s. All tests share a 15-minute budget, and a script that could end after it is reported as not run, which fails the job. Only `verify/<digits>.sh` runs; any other name fails the job. It sources `.github/scripts/verify-lib.sh` (`open_thunar`, `focus`, `wait_title`, `shot`, `pair`, `fail`). It drives Thunar with `xdotool`, asserts the result (window title, `xdotool` window queries, files on disk) and exits non-zero on failure. It creates its files in `$WORK`, and `shot` saves PNGs to `$SHOTS`. Name a before/after pair `before-<what>` and `after-<what>`, and describe it with `pair <what> "ACTION" "PROVES" "BEFORE-STATE" "AFTER-STATE" [GROUP]`: what the test did between the two shots, what the pair proves, the short states (at most 48 characters) on the image's bars, and its heading in the verify comment. A test that passes with a pair that has no `pair` call fails. Every `shot` states what it proves in one line, and each name is used once.
- `xdotool key` and `type` with `--window` send synthetic events that GTK ignores. Call `focus "$WID"` and send them without `--window`.
- To run the tests in a sandbox, as CI does: build, `mkdir -p dist && mv ../*.deb dist/`, then `.github/scripts/verify-proof.sh install` and `.github/scripts/verify-proof.sh run`. Shots, logs and the manifest `verify.tsv` land in `$OUT`, by default `${TMPDIR:-/tmp}/verify-proof/`. `install` replaces the system's Thunar, so never run it on the owner's machine. If the sandbox can't run Xvfb, write the script anyway: CI runs it.

## Context
Every turn re-reads the whole context, so a session's cost grows with it. Keep it small:
- Run noisy commands (`dpkg-buildpackage`, `verify-proof.sh`, `explainer-proof.sh`, `make-video.py`) as `cmd > "$LOG" 2>&1; echo "exit=$?"`, with `LOG` set to a file outside the repo, then `tail -n 30 "$LOG"`, or on failure grep it for the failing lines with the pattern its skill or agent gives. Never read a whole log, and never pipe the command into `tail`, which hides its exit code.
- Run the build and local verify in the `build-verify` agent (`.claude/agents/build-verify.md`), the local fresh-agent review of the diff in a `general-purpose` agent that returns only its findings, and the explainer's drafting and stamping as its skill says. Each returns the exact failing lines, not a paraphrase. `build-verify` installs the debs only in a cloud container, never on the owner's machine, runs the tests only against this branch's build, and runs `/visual-verify run:`'s capture. A session started before it existed runs a `general-purpose` agent told to read that file and follow it.
- Grep for a function, then Read only its lines with `offset` and `limit`. Don't re-read a file you edited this session. Never Read PNGs in the main context: screenshots go to the `shot-auditor`, and the explainer's render check to its subagent.

## Explainers
- Every issue PR adds `explainers/<issue>-<slug>.html` and `explainers/<issue>-<slug>.narration.json`, named after its `<issue>-<slug>` branch and written with the `explainer` skill (`.claude/skills/explainer/`). Not in `docs/`, which belongs to upstream. CI fails the PR without the page, renders it into the explainer comment, and runs `make-video.py status` on the narration. PRs from forks skip that job, so they aren't checked.
- Stamp the narration (`make-video.py stamp <issue>`) from the final page: after any later page edit, run `status`, rewrite the stale lines and stamp again. CI fails a narration that is missing or stale. In the cloud container set `CHROME` to the Playwright headless shell (see the skill). `phonemes` and `render` need Kokoro and stay on the owner's machine; `.claude/skills/explainer/videos-all.sh` renders every explainer's video there.

## CI review
- CI reviews every code push to a PR at `high`, with a 30-minute limit on the review itself, and by default pushes its fixes as a `claude[bot]` commit. It skips that fix commit, whatever its trailer, and any head a newer push has already replaced; the next push's review covers them. Run `git pull --rebase` before every push to a PR branch. A head commit with the trailer `Review: suggest` gets suggested changes instead of a fix commit; `Review: auto-fix` or `Review: suggest` on an empty commit forces a re-review. A `Review-accept: R23, R32` trailer on any commit in the PR closes those findings as accepted, so they stop failing the job. Re-running the `review-report` job alone after a successful review isn't supported and has no guards: it can report a pushed fix as not pushed and post suggestions twice.
- Read CI's PR comments (summary, review, verify, explainer) and the PR's checks only through the `pr-digest` agent (`.claude/agents/pr-digest.md`), passing the PR number and the last digest's head SHA and highest finding ID. Never fetch them with a full `get_comments` in the main context. To fix a finding, ask the digest for its `detail`: the review state's summary and its review thread, if any; read the code at its `file:line` for the rest. Scripts and skills that read a comment themselves, such as copying the verify comment's shots table, are unaffected. A session started before the agent existed runs a `general-purpose` agent told to read that file and follow it.
- One push per review round: collect the fixes for all of a review's findings into one push, not one per finding or thread.
- Fix the first review's findings. After that fix round, a `low` finding that isn't CONFIRMED, from any later review, is accepted rather than fixed, unless reading it confirms it as a bug that's quick to fix. Accept it on a commit that changes only `explainers/` (so no new review round starts), with a `Review-accept` trailer in the message's last paragraph that lists each ID separately: `Review-accept: R30, R31, R32`, never a range like `R30-R36`, which closes only R30 and R36. The explainer says which findings were accepted and why.
- A `low` finding from a later review with status `unconfirmed` counts as accepted, with no trailer. Every other finding, `unconfirmed` ones included, is fixed or brought to the owner. CI no longer re-checks an `unconfirmed` finding, so the fixing commit's message has a line naming each ID it fixes (`Fixes R4, R6`).

## Code comments and screenshots
- Don't add new explanatory code comments, in fixes and reviews too; when a change makes a comment stale, update it.
- Audit every screenshot before posting it or presenting it: run `/visual-verify` (`.claude/skills/visual-verify/`) on the captures, and fix the capture until it passes. CI posts its verify screenshots by itself, so after each CI run that took shots (not one whose build and verify ran `No code changed`) audit them from the `shots` branch (`/visual-verify pr:<n>`) and post the result as a PR comment that starts with `<!-- visual-verify <head sha> -->` and ends with its `VERDICT:` line. CI's summary shows the latest verdict posted for the head.
