PR for #157: renaming a file no longer frees its info while the window draws it

Branch 157-rename-main-thread → main, closes #157 (the PR number is assigned when it opens). F2, Enter no longer crashes Thunar: the rename job only renames the file on disk, and the window's own thread swaps the file's details afterwards.

Part 1

What this PR adds

The rename job in thunar-io-jobs.c now leaves the file's details alone on its worker thread; the new thunar_file_set_renamed in thunar-file.c updates them on the main thread.

runs on the main thread, which also draws the window runs on the rename job's worker thread

The big picture

On 26 November Thunar crashed right after an in-place rename (F2, type, Enter), closing every window. The crash was a read of a file's details that had already been freed. Thunar renames a file in a background job, and that job used to throw away the file's old details and load new ones while the window was still drawing the row from them. This PR moves that swap to the thread that draws, so drawing and swapping can no longer overlap.

Thunar keeps each file's details (name, size, icon, dates) in one shared object. Only the main thread may replace it, because the main thread is the one that reads it to draw rows, sort and fill the status bar. Nothing locks it against a second thread.

Step by step (numbers match the diagram)

  1. Rename starts. In-place rename with F2, the rename dialog, the name field in Properties, and undo or redo of a rename all call thunar_io_jobs_rename_file. It now also stores the file's current location (its GFile) in the job, read here on the main thread, so the worker never reads it from the shared file object.
  2. Rename on disk. On the worker thread the job calls g_file_set_display_name on that stored location. It renames the real file and returns the new location. It no longer calls thunar_file_rename, which also swapped the file's details right there on the worker thread: the cause of the crash.
  3. Hand over. The job passes the file and its new location to _thunar_io_jobs_rename_notify with exo_job_send_to_mainloop. That call blocks the worker until the main thread has run the callback, so steps 4 and 5 finish before step 6 starts.
  4. Swap the info. On the main thread, the new thunar_file_set_renamed points the file at its new location (thunar_file_replace_file) and reloads its details (thunar_file_load). Nothing else can be drawing at that moment, because drawing happens on this same thread.
  5. Tell the views. As before, thunarx_file_info_renamed tells the folder, and thunar_file_changed makes the views redraw the row with the new name.
  6. Undo entry. Back on the worker, when the rename should be undoable, the job records the old and the new location, taken straight from step 1 and step 2. Ctrl+Z uses that entry to rename the file back. Then the job finishes.

Before and after

Before: the worker swapped the details

The job called thunar_file_rename on its worker thread, which freed the old details and loaded new ones. If the window drew that row at the same moment, it read freed memory and Thunar crashed.

Now: the main thread swaps them

The worker only renames the file on disk. The main thread, which does all the drawing, swaps the details, so a draw never sees them half-replaced or freed.

  /* worker thread: rename on disk only */
  renamed_file = g_file_set_display_name (old_file, display_name, cancellable, &err);

  /* main thread: _thunar_io_jobs_rename_notify */
  thunar_file_set_renamed (file, data->renamed_file);
  thunarx_file_info_renamed (THUNARX_FILE_INFO (file));
The bulk renamer still calls thunar_file_rename itself, on the main thread, so it never had this race. That function is left as it is, to keep the next upstream merge simple.

Built on 3 known-good references

Issue #157's analysis

The kernel log and libgio's debug info put the crash in g_file_info_find_value on the main thread; the issue traced the worker-thread swap and proposed this fix.

exo's job code

exo/exo-job.c on exo's master branch: exo_job_send_to_mainloop wraps a GLib call that blocks the worker until the callback returns.

Thunar's own folder monitor

When a file is renamed outside Thunar, the monitor already swaps the details on the main thread. The rename job now does the same.

Code review

Before the first push, /code-review at high reviewed the branch: 6 findings, 1 fixed, 5 left as they are.

  • Fixed: the worker read the file's location from the shared file object while the main thread could replace it. The job now takes the location on the main thread when it is created.
  • Left, unconfirmed: a late "renamed" event from the folder monitor might reload a name that no longer exists. That path already reloads on the main thread, and the 30-rename test passed.
  • Left, accepted: reloading the details now runs on the main thread, so a rename on a slow network mount briefly holds up the window, as the monitor's own reload already does.
  • Left for the upstream merge: thunar_file_rename's called_from_job option is now unused; removing it would conflict with upstream.
  • Done or ruled out: the missing explainer is this page, and a cancelled job can't skip the main-thread step, because that step runs before the job returns.

Glossary

Main thread
The thread that draws Thunar's windows and handles your keys and clicks.
Worker thread
A background thread that runs slow file work, so the window stays responsive.
Rename job
The background task that renames one file, started by every rename except the bulk renamer.
GFile
GLib's handle for a file's location, such as its path.
GFileInfo
GLib's record of a file's details: name, size, type, dates, icon.
ThunarFile
Thunar's shared object for one file, holding its GFile and GFileInfo.
Use-after-free
Reading memory after it was released; it crashes or reads garbage.
Race
A bug that shows only when two threads happen to act at the same moment.
exo_job_send_to_mainloop
Runs a function on the main thread and makes the job wait until it returns.
AddressSanitizer
A build option that stops a program at the first use of freed memory.
In-place rename
F2 edits the name right in the file list (#16), instead of in a dialog.
Undo log
Thunar's list of recent file operations that Ctrl+Z and Ctrl+Shift+Z replay.
Upstream
Xfce's own Thunar, which this fork merges from.
verify/157.sh
The test script CI runs: it drives Thunar with xdotool and takes screenshots.
Smoke test
Checks that Thunar is still running 10 s after it starts.
/visual-verify
A check that each screenshot shows what the test says it proves.
