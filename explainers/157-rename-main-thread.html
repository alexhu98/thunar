PR #158: renaming a file no longer frees its info while the window draws it

Branch 157-rename-main-thread → main, closes #157. F2, Enter no longer crashes Thunar: the rename job still renames the file on disk on its worker thread, but the window's own thread swaps the file's details, and nothing can delete the file in between.

Part 1

What this PR adds

The rename job in thunar-io-jobs.c still renames on its worker thread, but it marks the file first and swaps the file's details on the main thread with the new thunar_file_set_renaming and thunar_file_set_renamed in thunar-file.c.

runs on the main thread, which also draws the window runs on the rename job's worker thread

The big picture

On 26 November Thunar crashed right after an in-place rename (F2, type, Enter), closing every window. The crash was a read of a file's details that had already been freed. Thunar renames a file in a background job, and that job used to throw away the file's old details and load new ones while the window was still drawing the row from them. This PR moves that swap to the thread that draws, so drawing and swapping can no longer overlap. The slow disk work stays in the background.

Thunar keeps each file's details (name, size, icon, dates) in one shared object. Only the main thread may replace it, because the main thread is the one that reads it to draw rows, sort and fill the status bar. Nothing locks it against a second thread.
The catch: once the file is renamed on disk, Thunar's watchers see the old name vanish and report it deleted, which would destroy the file object before the main thread swaps it. So the file is marked as renaming for the whole job: a delete or reload for it is held, and the file is reloaded once after the swap.

Step by step (numbers match the diagram)

  1. Rename starts. In-place rename with F2, the rename dialog, the name field in Properties, and undo or redo of a rename all call thunar_io_jobs_rename_file. It stores the file's current location (its GFile) in the job, read here on the main thread, so the worker never reads it from the shared file object.
  2. Mark renaming. The worker's first act is to run _thunar_io_jobs_rename_begin on the main thread, which sets the new THUNAR_FILE_FLAG_RENAMING with thunar_file_set_renaming. While it is set, thunar_file_destroy and thunar_file_reload don't act on this file: they set a second flag, THUNAR_FILE_FLAG_RENAME_HELD, to remember that something arrived. So a "deleted" or reload for the old name, from the file's own watch or a folder monitor, can't destroy it mid-rename, and isn't forgotten either.
  3. Rename on disk. On the worker thread the job calls g_file_set_display_name on the stored location, which renames the real file and returns the new location. Then g_file_query_info reads the new details. Both can block on a slow disk, so they stay off the thread that draws.
  4. Hand over. The job passes the new location and details to _thunar_io_jobs_rename_notify with exo_job_send_to_mainloop. That call blocks the worker until the main thread has run the callback, so data on the worker's stack stays valid, and steps 5 and 6 finish before the job does.
  5. Swap the info. On the main thread the callback clears the mark; thunar_file_set_renaming now also says whether a destroy or reload was held. Then the new thunar_file_set_renamed points the file at its new location and installs the new details (or loads them, if reading them failed). Nothing else can be drawing at that moment, because drawing happens on this same thread. If the rename failed, it reloads the file instead, as before.
  6. Tell and log. As before, thunarx_file_info_renamed tells the folder and thunar_file_changed makes the views redraw the row. Then, when the rename should be undoable, the callback records the old and new location in the undo log, on the main thread and after the swap. Ctrl+Z uses that entry to rename the file back. Last, if a destroy or reload was held, it reloads the file; a file that is gone from disk is destroyed by that reload, so a real deletion during the rename still lands.

Before and after

Before: the worker swapped the details

The job called thunar_file_rename on its worker thread, which freed the old details and loaded new ones. If the window drew that row at the same moment, it read freed memory and Thunar crashed.

Now: the main thread swaps them

The worker renames the file on disk and reads its new details. The main thread, which does all the drawing, swaps them in, so a draw never sees them half-replaced or freed.

In between: the mark

From before the rename on disk until the swap, the file is marked as renaming. Thunar's watchers can't destroy or reload it then, so the swap always finds the same, live file object. Anything they reported is held, and one reload after the swap catches up on it.

  /* worker thread: _thunar_io_jobs_rename */
  exo_job_send_to_mainloop (job, _thunar_io_jobs_rename_begin, data.file, NULL);
  data.renamed_file = g_file_set_display_name (data.old_file, display_name, cancellable, &err);
  data.info = g_file_query_info (data.renamed_file, ...);
  exo_job_send_to_mainloop (job, _thunar_io_jobs_rename_notify, &data, NULL);

  /* main thread: _thunar_io_jobs_rename_notify */
  held = thunar_file_set_renaming (file, FALSE);
  thunar_file_set_renamed (file, data->renamed_file, data->info);
  thunarx_file_info_renamed (THUNARX_FILE_INFO (file));
  if (held)
    thunar_file_reload (file);
The bulk renamer calls thunar_file_rename itself, on the main thread, so it never had this race. That function loses its unused called_from_job option and now reuses thunar_file_set_renamed. The Properties dialog also ignores Enter while its own rename job is still running, so it can't start a second one.

Part 2

How it was built and verified

The final design was built and tested in the cloud container, at commit e9298220d, before CI's one-finding fix be890a15b, which only CI builds and tests. A race can't be forced on demand, so the test lowers the risk rather than proving the fix.

Built on 3 known-good references

Issue #157's analysis

The kernel log and libgio's debug info put the crash in g_file_info_find_value on the main thread; the issue traced the worker-thread swap and proposed this fix.

exo's job code

exo/exo-job.c on exo's master branch: exo_job_send_to_mainloop wraps a GLib call that blocks the worker until the callback returns.

Thunar's own folder monitor

When a file is renamed outside Thunar, the monitor already swaps the details on the main thread. The rename job now does the same.

How the design got here

  1. First version. The worker renamed on disk and handed the swap to the main thread, which also reloaded the details there.
  2. Local review. It found the worker still read the file's location from the shared object; the job now takes it on the main thread when it is created.
  3. CI's review. CI reviewed that push at high (run 45915196233) and found 7 things, R1 to R7. The serious one, R1: in the gap between the rename on disk and the swap, a watcher could report the old name deleted and destroy the file.
  4. CI's own fix. Its fix commit moved the whole rename, disk work included, onto the main thread, which closes the gap but makes the window wait on the disk.
  5. The owner's choice. Keep the disk work on a worker thread, as the issue planned, and close the gap another way: the renaming mark. That is this design, in commit e9298220d.

Code review

Before the first push, /code-review at high reviewed the branch: 6 findings, 1 fixed, 5 left as they are.

  • Fixed: the worker read the file's location from the shared file object while the main thread could replace it. The job now takes the location on the main thread when it is created.
  • Left, unconfirmed: a late "renamed" event from the folder monitor might reload a name that no longer exists. That path already reloads on the main thread, and the 30-rename test passed.
  • Left at first, fixed later: reloading the details on the main thread could briefly hold up the window on a slow network mount. CI raised it again as R4, and the final design reads them on the worker.
  • Left at first, removed later: thunar_file_rename's unused called_from_job option. CI raised it as R7, and it is gone.
  • Done or ruled out: the missing explainer is this page, and a cancelled job can't skip the main-thread step, because that step runs before the job returns.

CI's code review

CI's review of the first push (run 45915196233, high) found 7 things, and its review of the final design, e9298220d, found one more. All are handled:

  • R1, high, fixed: a watcher could report the old name deleted and destroy the file before the swap. The renaming mark holds that off.
  • R2, medium, covered: the late swap could put a destroyed file back in Thunar's file cache. The file can't be destroyed during the rename any more.
  • R3, medium, not a bug: the undo entry might be logged before the swap. The hand-over blocks the worker, and the entry is now logged on the main thread, after the swap.
  • R4, low, fixed: reading the new details blocked the main thread. The worker reads them now.
  • R5, low, fixed: logging the undo entry on the worker updated toolbar buttons off the main thread. It is logged on the main thread now.
  • R6, low, fixed by CI: Properties could start a second rename job if focus left right after Enter. It ignores Enter while a job runs.
  • R7, low, fixed: an unused option and a copied code path in thunar_file_rename. Both are gone.
  • R8, fixed by CI: a destroy or reload that arrived while the file was marked was thrown away, so a real deletion in that moment was lost. CI's fix commit be890a15b holds it instead and reloads the file after the swap.

Every finding, with CI's later reviews, is in the PR's code review comment.

Glossary

Main thread
The thread that draws Thunar's windows and handles your keys and clicks.
Worker thread
A background thread that runs slow file work, so the window stays responsive.
Rename job
The background task that renames one file, started by every rename except the bulk renamer.
GFile
GLib's handle for a file's location, such as its path.
GFileInfo
GLib's record of a file's details: name, size, type, dates, icon.
ThunarFile
Thunar's shared object for one file, holding its GFile and GFileInfo.
Use-after-free
Reading memory after it was released; it crashes or reads garbage.
Race
A bug that shows only when two threads happen to act at the same moment.
exo_job_send_to_mainloop
Runs a function on the main thread and makes the job wait until it returns.
AddressSanitizer
A build option that stops a program at the first use of freed memory.
In-place rename
F2 edits the name right in the file list (#16), instead of in a dialog.
Undo log
Thunar's list of recent file operations that Ctrl+Z and Ctrl+Shift+Z replay.
Renaming mark
The new THUNAR_FILE_FLAG_RENAMING: while set, Thunar holds that file's destroy and reload until the swap.
File monitor
GLib's watcher that tells Thunar when a file or folder changes on disk.
R1 to R8
IDs CI's code review gives its findings, in its PR comment.
Upstream
Xfce's own Thunar, which this fork merges from.
verify/157.sh
The test script CI runs: it drives Thunar with xdotool and takes screenshots.
Smoke test
Checks that Thunar is still running 10 s after it starts.
/visual-verify
A check that each screenshot shows what the test says it proves.
