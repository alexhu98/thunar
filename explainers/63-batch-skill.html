Part 1

What this PR adds

One new skill file, .claude/skills/batch/SKILL.md: an orchestrator that plans, tracks and starts child sessions, and checks on them without reading any PR noise.

the orchestrator session a child session, one per group you

The big picture

On 8 November one session handled ten CI issues in grouped PRs and reached 654 thousand tokens of context for two PRs. Most of it was PR noise the next group never needed: GitHub notifications, CI's comments and review rounds. With /batch, each group gets a fresh session that carries that noise and ends when its PR merges, and the session you talk to keeps only a status line per group.

The orchestrator never subscribes to a PR and never reads CI's comments. It looks only at each child's status and whether its PR merged, the way /visual-verify keeps only the shot auditor's verdict.

Step by step (numbers match the diagram)

① Orchestrator
  1. Plan. /batch 48 52-60 reads each open issue, notes the files it touches and what it depends on, and prints one table of groups, branches and order, with the number of PRs (each costs CI minutes).
  2. You confirm. The turn ends with one "What I need from you" question. You reply with one number or letter, and can add a stop point such as "stop after group B".
  3. Track. It opens a tracking issue titled Batch: #…, with one checklist row per group: issues, branch, session, PR and status. The body is the batch's state, so a check-in can rebuild from it.
  4. Run a group. create_session starts a child with a fixed brief, copied from the brief that ran #56 and #66: follow CLAUDE.md, one branch from origin/main, a stamped explainer, a local review, merge under the merge rule, and report back in one line.
② Child session and check-ins
  1. Child merges. The child does the whole PR loop on its own, posts a line on the tracking issue when it opens the PR, merges or gets blocked, and tells the orchestrator with send_message.
  2. Watch cheaply. Each child reports its own events: PR opened, blocked with its question, resumed, merged. A blocked child's question reaches you once, and you answer it in the child's session. A send_later check-in every 90 minutes is only a safety net: it reads get_session's status and flags a child that stopped without reporting, once, until that child speaks again.
  3. Stop. At the stop point or after the last merge, it cancels the pending check-in, closes the tracking issue and reports how many groups merged.

Rules the skill keeps

One group at a time

The next group starts only after the last one merges. Two run at once only when the plan you confirmed says their files don't overlap.

You answer the child

A child's permission check may refuse an approval relayed from another session, so the orchestrator points you to the child instead of passing answers on.

No PR work here

The orchestrator never commits, reviews or merges. A check-in that would need more than a few calls asks you first.

Code review

A fresh agent, given only the skill and the issue, found 9 problems: 2 high, 4 medium, 3 low. 8 are fixed; one was kept on purpose.

  • Check-ins: they could pile up, and a check-in message could start a new batch. Now only one is ever pending, and check-in #<t> is its own argument.
  • Finding the PR: a PR merged between check-ins was missed. The lookup now includes merged PRs.
  • Child brief: "owner-approved" could read as leave to merge anything. It now says merge when the merge rule allows it, and ask the owner otherwise.
  • Smaller fixes: PR numbers in a range are skipped, a stall needs the PR to stop changing, and the tracking issue closes as completed.
  • Kept: the brief's local fresh-agent review. The explainer skill already expects one, and the brief that ran #70 asked for it.

CI's first review found 9 more (R1–R9: 4 medium, 5 low), all fixed in one push. Each group's row in the tracking issue now holds its start time, the PR's last update and its notes; closed, failed and resumed children each have a case; and the brief asks for /visual-verify as CLAUDE.md says rather than for a PASS. Details are in the code review PR comment.

Its second review found 9 more (R10–R18), all about when the owner is told. Step 4 was rewritten around one rule: each check-in works out a child's condition (merged, closed, failed, blocked, stalled or ok) and tells the owner only when it differs from the last thing they were told. A second fresh agent traced nine scenarios through it, and its six findings are fixed in the same push. The PR is found with one GitHub search that returns no PR body.

The third review found 9 more (R19–R27), fixed in one push: the batch no longer runs past its stop point, a child also reports its PR number and when it resumes, a child working for hours with no PR is flagged again, and a batch where only failed or closed groups remain waits for the owner instead of checking in forever.

The fourth review still found new edge cases in that inference, so the owner chose to simplify it: the children's messages now carry every event, a check-in only flags a child that stopped without reporting, and one waiting on owner mark per group stops repeats. The open findings from that review (R19, R23, R28–R34) were all about the inference that is now gone.

CI's review of the simpler design found 8 more (R35–R42). Fixed: the merge message records the PR number, a recovered restart no longer alerts you, the PR is read with a search that returns no body, a slow 4-hour check-in keeps running while every child waits on you, an idle child whose PR isn't merged is flagged, and a failed group can be skipped. A child that is still working is never flagged (R36); you accepted it.

The next review found 9 more (R43–R51). Fixed: a skipped group is marked as skipped rather than merged, groups that depend on it wait for your word, a waiting child that merged is still noticed, and a closed PR is named as closed. Three are limits of a safety net that only looks every 90 minutes (R41, R43, R49): at worst you get one extra flag. You accepted them with R36.

The review of those fixes found 7 more about skipped groups (R52–R58), all fixed: a skipped group stays skipped if its child speaks again, stops the check-ins, counts at the stop point, and you are asked whether the groups after it should start.

The last review found 6 more (R59–R64), fixed: skipping a group starts the groups that may now start, a group you decline to start is skipped too, and the closed tracking issue names the skipped groups. You accepted four findings as limits of a safety net that only looks every 90 minutes (R36, R41, R43, R49): at worst you get one extra flag, and a child that keeps working without a PR shows in your session list.

Glossary

Orchestrator
The session you run /batch in. It plans and tracks, and never touches a PR.
Child session
A fresh cloud session started for one group, which builds and merges that group's PR.
status_bucket
A session's state in one word: working, blocked, review_ready, completed or failed.
send_later
A one-shot message back into this session at a set time, used for check-ins.
Tracking issue
The GitHub issue holding the batch's checklist, one row per group.
