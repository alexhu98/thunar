Part 1

What this PR adds

The workflow that runs from now on, on every PR and every merge, and the files that make it.

runs on every PR runs only after a merge

The big picture

You change Thunar's source code, but your machines don't run source code: they run installed packages (.deb files, Ubuntu's installer format). Turning source into .debs means about 3 minutes of compiling on a machine that has the right libraries. This PR makes GitHub do that on its own servers every time the code changes, and, once you approve a change, publish the .debs where your machines can download them.

One file, .github/workflows/build.yml, drives everything below. It runs on two different events: a pull request (lane ①) and a push to main (lane ②). Some steps check which event it is and run only for one of them.

Step by step (numbers match the diagram)

① Pull request: prove it builds
  1. Open or update a PR. Someone pushes commits to a branch (this one is 1-ci-build) and opens a pull request asking to merge it into main. GitHub sees the on: pull_request trigger in build.yml and starts the workflow. Every new push to the branch starts it again; the older run is cancelled.
  2. build job. GitHub lends a fresh, empty Ubuntu 24.04 virtual machine (a runner). It adds Zorin's PPA, so it gets the same Xfce 4.20 libraries your machines have, and installs everything debian/control lists under Build-Depends (apt-get build-dep ./). On a PR it also dry-runs the three release scripts against the real repo, so a bug in them fails here instead of after the merge. Then dpkg-buildpackage -b compiles Thunar, runs its test, and wraps the result into .debs, following the recipe in debian/. The machine is thrown away afterwards.
  3. Artifact. The 5 .debs are saved as a zip on the run's page for 14 days, and the PR gets a green check. Nothing is published. The version is the placeholder +local0, so if anyone installed it by accident, apt would treat it as older than your +local1 and refuse to replace it without asking.
  4. You review and merge. The only human step and the only gate: read “Files changed”, confirm the check is green, click Merge. Before this click, no release can exist.
② Push to main: version and publish
  1. Push to main. Merging adds a commit to main, which is a push, a different trigger (on: push). The same workflow runs again, and now the steps marked if: github.event_name == 'push' run too. concurrency makes two quick merges wait in line instead of running together, so they can't pick the same version number. Only one run waits at a time: if a third merge lands meanwhile, GitHub cancels the waiting run and queues the newest one, whose build already includes the skipped merge.
  2. Stamp the version. next-version.sh asks GitHub for the existing releases and v* tags, takes the highest +localN and adds 1 (never below 2). It writes that version as a new top entry in debian/changelog, only on the throwaway machine; it's never committed. This matters because apt decides “is this newer?” by comparing version strings, so each build must sort higher than the last.
  3. build job. The same compile as step 2, now producing .debs with the real version, 4.20.10-1~bpo24.04+local2.
  4. release job. A second job that starts only after the build succeeds (needs: build) and is the only one allowed to write to the repo. It downloads the build's .debs and publish-release.sh creates a GitHub Release called v4.20.10+local2: a download page tied to a git tag. It attaches the 3 packages your machines need; the other 2 (-dev, gir1.2) are only for building plugins. It publishes only a commit newer than the one the highest +localN tag points at, so re-running an old run can't put older code on top; re-running a failed release job re-uploads to the same release. Then prune-releases.sh deletes everything except the newest 10 releases.
Rollback: delete the bad release on GitHub. Once the updater from #2 exists, its next hourly check finds the previous release as the newest one and installs it, even though it's a lower version. Leave its tag in place (with gh release delete, omit --cleanup-tag): the next build counts it and takes a higher number, so the fix never reuses the bad version.

What's in debian/: Zorin's packaging with 4 edits

1. Bootstrap from git

A git checkout has no configure or generated files. Run Thunar's own autogen.sh, then configure with --enable-maintainer-mode so generated files like thunar-marshal.c are built.

2. Plugin path without a patch

Zorin patched the source to also load plugins from /usr/lib/thunarx-3. Thunar's own --with-thunarx-dirs option does the same, so the patch and debian/patches/ are gone. So is gbp.conf, which named branches this repo doesn't have.

3. Changelog at +local0

A placeholder below your installed +local1. CI swaps in the real number at build time and never commits it.

4. Tests run again

The only test, abicheck.sh, failed in every build, Zorin's included, on 4 exported thunarx_provider_module_* symbols missing from thunarx/thunarx.symbols. They're listed now, so it passes.

How it was built and verified

Where the packaging came from, what was checked and how, and what can only be checked after the merge.

Built on two known-good references

Zorin's packaging

debian/ is copied from Zorin's thunar_4.20.2-1~bpo24.04, the package your machines ran before, so package names, file lists and dependencies start out the same as Zorin's.

Your hand build, +local1

The 5 .debs in Thunar-debs/local-4.20.10/, already installed on the desktop. Each build in the table below was compared against them: same files, same dependencies.

Build from git, not the tarball

The release tarball's pre-generated gdbus files need GLib 2.84; Ubuntu 24.04 has 2.80. A git checkout regenerates them, which is why edit 1 bootstraps with autogen.sh and maintainer mode.

Code review

An xhigh code review of the whole diff found 11 issues. All are fixed in this PR:

  • Releases: a rollback could reuse the deleted version number; re-running an old run could publish older code as the newest release; re-running a failed release job always failed.
  • Safety: the GitHub token was visible to the build scripts of every PR; now only the steps that call GitHub get it.
  • Coverage: PRs never ran the release scripts (now dry-run on every PR); the test step was switched off instead of fixed (edit 4).
  • Packaging: Zorin's plugin-path patch ignored THUNARX_DIRS (replaced by a configure option); gbp.conf was dead config.
  • Docs: this page misdescribed queued runs; the changelog said CI replaces +local0 instead of adding an entry above it; a script needed an undocumented variable.

What comes later: #7, then #2

Two open issues build on these releases. #7 comes first, so features reach your machines only through PRs that CI has proven.

#7 Cloud agents open PRs, CI proves them (next)

  1. Repo CLAUDE.md. Cloud sessions can't see your personal instructions, so the repo carries them: branch and PR naming, the build lessons from Part 2, a verify/<issue>.sh in every feature PR, and explainers like this page in explainers/.
  2. Ported skills. The screenshot audit and visual-verify skills from your other project, with Storybook swapped for Xvfb, xdotool and import.
  3. verify job. Added to this PR's build.yml, after the build: install the 3 .debs, start Thunar under Xvfb and check it stays up, run each verify/*.sh, and post the results and before/after screenshots as a PR comment.
  4. Sandbox check. One cloud session first checks that it can build and run Thunar itself. If it can't, the agent still writes the code and only CI builds and verifies.

#2 Auto-deploy to the desktop and laptop (after #7)

  1. GitHub Releases. The shelf the machines take from. Because the repo is private, they need a token to read it.
  2. thunar-update. A small script on each machine, run by a systemd timer: 2 minutes after boot, then every hour. It asks GitHub for the newest release using a read-only token.
  3. apt installs the 3 .debs. Only if that release's version differs from what's installed, so a rollback to a lower version installs too. A Thunar that is already running keeps the old code in memory until it restarts.
  4. Notification. “Restart Thunar to load it.” It never restarts Thunar for you, because that would close all your windows.

Glossary

CI
Continuous integration: a server builds and checks every change automatically.
Workflow
A YAML file in .github/workflows/ telling GitHub Actions what to run, and when.
Trigger
The event that starts a workflow: here pull_request or push to main.
Runner
The throwaway virtual machine GitHub lends to run a job.
Job / step
A job runs on one runner; it is a list of steps (shell commands or ready-made actions).
Artifact
Files a run keeps for download afterwards; here a zip of .debs kept 14 days.
Release / tag
A tag names one commit; a release is a download page for that tag with attached files.
.deb
An Ubuntu/Debian package: compiled program, its files, and its dependency list.
apt
Ubuntu's package manager; installs .debs and compares versions to decide what's newer.
PPA
An extra package source; ppa:zorinos/stable supplies Zorin's Xfce 4.20 libraries.
debian/
The recipe for turning this source tree into .debs (build steps, dependencies, file lists).
Changelog
debian/changelog; its top entry sets the package version.
Maintainer mode
A configure option that regenerates generated source files; needed when building from git.
Xvfb
A virtual screen with no monitor, so CI can run and screenshot a desktop app.
