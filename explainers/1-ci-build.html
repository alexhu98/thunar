PR #8: CI-built Thunar .debs

Branch 1-ci-build → main. One workflow, two paths: a PR only builds; a merge builds, versions and publishes. Issue #2 later picks up the releases.

The big picture

You change Thunar's source code, but your machines don't run source code: they run installed packages (.deb files, Ubuntu's installer format). Turning source into .debs means about 3 minutes of compiling on a machine that has the right libraries. This PR makes GitHub do that on its own servers every time the code changes, and, once you approve a change, publish the .debs where your machines can download them.

One file, .github/workflows/build.yml, drives everything below. It runs on two different events: a pull request (lane ①) and a push to main (lane ②). Some steps check which event it is and run only for a push.

Step by step (numbers match the diagram)

① Pull request: prove it builds
  1. Open or update a PR. Someone pushes commits to a branch (here 1-ci-build) and opens a pull request asking to merge it into main. GitHub sees the on: pull_request trigger in build.yml and starts the workflow. Every new push to the branch starts it again; the older run is cancelled.
  2. build job. GitHub lends a fresh, empty Ubuntu 24.04 virtual machine (a runner). It adds Zorin's PPA, so it gets the same Xfce 4.20 libraries your machines have, and installs everything debian/control lists under Build-Depends (apt-get build-dep ./). Then dpkg-buildpackage -b compiles Thunar and wraps the result into .debs, following the recipe in debian/. The machine is thrown away afterwards.
  3. Artifact. The 5 .debs are saved as a zip on the run's page for 14 days, and the PR gets a green check. Nothing is published. The version is the placeholder +local0, so if anyone installed it by accident, apt would treat it as older than your +local1 and refuse to replace it without asking.
  4. You review and merge. The only human step and the only gate: read “Files changed”, confirm the check is green, click Merge. Before this click, no release can exist.
② Push to main: version and publish
  1. Push to main. Merging adds a commit to main, which is a push, a different trigger (on: push). The same workflow runs again, and now the steps marked if: github.event_name == 'push' run too. concurrency makes two quick merges wait in line instead of running together, so they can't pick the same version number.
  2. Stamp the version. next-version.sh asks GitHub for the existing releases, takes the highest +localN and adds 1 (never below 2). It writes that version as a new top entry in debian/changelog, only on the throwaway machine; it's never committed. This matters because apt decides “is this newer?” by comparing version strings, so each build must sort higher than the last.
  3. build job. The same compile as step 2, now producing .debs with the real version, 4.20.10-1~bpo24.04+local2.
  4. release job. A second job that starts only after the build succeeds (needs: build) and is the only one allowed to write to the repo. It downloads the build's .debs and creates a GitHub Release called v4.20.10+local2: a download page tied to a git tag. It attaches the 3 packages your machines need; the other 2 (-dev, gir1.2) are only for building plugins. Then prune-releases.sh deletes everything except the newest 10 releases.
③ Machines pick it up (issue #2, not built yet)
  1. GitHub Releases. The shelf the machines take from. Because the repo is private, they need a token to read it.
  2. thunar-update. A small script on each machine, run by a systemd timer: 2 minutes after boot, then every hour. It asks GitHub for the newest release using a read-only token.
  3. apt installs the 3 .debs. Only if that release's version differs from what's installed. A Thunar that is already running keeps the old code in memory until it restarts.
  4. Notification. “Restart Thunar to load it.” It never restarts Thunar for you, because that would close all your windows.
Rollback: delete the bad release on GitHub. On the next hourly check the previous release is the newest one, so the machines install it, even though it's a lower version.

What's in debian/: Zorin's packaging with 3 edits

1. Bootstrap from git

A git checkout has no configure or generated files. Run Thunar's own autogen.sh, then configure with --enable-maintainer-mode so generated files like thunar-marshal.c are built.

2. Skip the test step

Its only test, abicheck.sh, fails in every build, Zorin's included, on 4 extra thunarx_provider_module_* symbols.

3. Changelog at +local0

A placeholder below your installed +local1. CI swaps in the real number at build time and never commits it.

Glossary

CI
Continuous integration: a server builds and checks every change automatically.
Workflow
A YAML file in .github/workflows/ telling GitHub Actions what to run, and when.
Trigger
The event that starts a workflow: here pull_request or push to main.
Runner
The throwaway virtual machine GitHub lends to run a job.
Job / step
A job runs on one runner; it is a list of steps (shell commands or ready-made actions).
Artifact
Files a run keeps for download afterwards; here a zip of .debs kept 14 days.
Release / tag
A tag names one commit; a release is a download page for that tag with attached files.
.deb
An Ubuntu/Debian package: compiled program, its files, and its dependency list.
apt
Ubuntu's package manager; installs .debs and compares versions to decide what's newer.
PPA
An extra package source; ppa:zorinos/stable supplies Zorin's Xfce 4.20 libraries.
debian/
The recipe for turning this source tree into .debs (build steps, dependencies, file lists).
Changelog
debian/changelog; its top entry sets the package version.
Maintainer mode
A configure option that regenerates generated source files; needed when building from git.
