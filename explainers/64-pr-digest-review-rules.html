Part 1

What this PR adds

A read-only pr-digest agent in .claude/agents/, and four rules in CLAUDE.md on how the agent reads and answers CI's reviews.

same as before new in this PR

The big picture

On PR #62, CI's review raised 36 findings over 7 pushes, none of them confirmed. The session read the review comment, up to 60,000 characters, in full several times just to find each round's new ones, and every fix push drew about 7 new low findings. It took three owner decisions to end that loop.

CI writes its state as JSON in hidden comment markers. The digest reads those, so it counts every finding even when the Markdown table is cut to fit, and it always prints the totals, so a finding it leaves out is still counted.

Step by step (numbers match the diagram)

① Reading a PR: through pr-digest
  1. Ask the digest. Whenever the session needs a PR's CI state, it starts the pr-digest agent with the PR number and, after the first time, the last digest's head SHA and highest finding ID. CLAUDE.md now forbids a full get_comments in the main session.
  2. Read in full. The agent has only GitHub read tools, plus Read and Grep for CLAUDE.md. It reads the PR, its check runs, its commits, every comment and the review threads, in its own context.
  3. Parse markers. It parses <!-- review:state {...} --> for each finding's ID, severity, verdict and status, and <!-- pr-proof:status {...} --> for each check's state and the commit it covers. It also reads each commit's Review-accept trailer and flags a range like R30-R36, and checks whether build, verify and explainer ran their steps.
  4. About 20 lines. Head, base and whether main moved; each check; finding totals by status; the new findings, one line each; the open ones split by low-unconfirmed and the rest; the latest /visual-verify verdict; unanswered owner comments; and one line on the merge rule.
② Answering a review round
  1. One push. All the fixes for one review's findings go out together, so each round costs one CI run and one new review.
  2. Accept the lows. After that one fix round, a low finding that isn't CONFIRMED, from any later review, is accepted, unless reading it shows a real bug that's quick to fix. It is accepted on a commit that changes only explainers/, which CI doesn't review, with Review-accept: R30, R31, each ID listed. A low finding already marked unconfirmed counts as accepted with no trailer.
  3. The rest. A medium or high finding, or a CONFIRMED one, is fixed or brought to the owner, as before. That includes unconfirmed ones: CI stops re-checking them, so the fixing commit's message names each ID, as in Fixes R4.
  4. Merge rule. "Every review finding is fixed" becomes "fixed, resolved or accepted under the CI review rules, none closed by a Review-accept the agent added outside them".

Code review

A fresh agent, given only the diff and the two issues, found 8: 2 high, 3 medium, 3 low. All 8 are fixed. The first test run on PR #62 also showed the digest listing all 36 findings and judging the merge rule by the old wording; both are fixed.

  • Unconfirmed isn't always low: CI marks any plausible finding unconfirmed after a round, medium and high too. Only low ones now count as accepted; the rest still need a fix or the owner.
  • What the digest can see: the review's skip reason is read from its one Markdown line, and whether jobs ran their steps comes from the run's job list.
  • Smaller ones: whether main moved has a defined test; the trailer goes in the message's last paragraph; the merge rule names resolved findings too; an escape note had lost its backslash.

CI's first review, at high in 4 minutes, found 9 more: 5 medium, 4 low, one of them confirmed. All 9 are fixed in one push. The digest now reads which commit fixed an unconfirmed finding from its message, judges whether main moved by dates, and can return a finding's full text. The rules now say which reviews' lows are accepted, and that scripts reading a comment themselves are unaffected. Its second review found 7 more, R10–R16, 5 of them confirmed. All 7 are fixed in a second push: main counts as moved unless the branch already contains it, a Fixes line must touch the finding's file, and only a later review's lows are accepted without a fix. Its third review found 8 more. The 3 confirmed ones are fixed in a third push: one digest line lists every unsettled finding, a Fixes line in another file is flagged rather than refused, and findings cut from the state count as unsettled. The 5 lows that aren't confirmed are accepted under the new rule, on an explainer-only commit: R20–R24, about edge cases in the digest's own method (a PR whose first review found nothing, a very long ancestry walk, extra API calls and wording). The fourth review found 6: the 3 confirmed ones (trimmed closed findings, a mark no line showed, first-review lows not marked) are fixed in a fourth push, and the 3 lows, R28–R30, are accepted the same way, about trimmed findings and line count. The fifth review passed, with 4 findings none of them confirmed: the 2 mediums and 1 low, about findings cut from the state, are fixed, and R33, a low that would change CI's own script, is accepted. The code review comment on PR #67 has every finding.

Glossary

Agent
A helper Claude session with its own context and a limited set of tools.
Digest
The short status pr-digest returns in place of CI's full comments.
Marker
A hidden HTML comment in a PR comment that holds CI's data as JSON.
Finding
One problem CI's review reports, numbered R1, R2 and so on.
CONFIRMED / plausible
Whether the review reproduced a finding or only suspects it.
unconfirmed
A plausible finding left open for a round, which CI stops re-checking.
Trailer
A Key: value line at the end of a commit message, such as Review-accept: R30, R31.
