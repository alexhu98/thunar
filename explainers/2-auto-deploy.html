Part 1

What this PR adds

A new deploy/ folder: an updater script, the systemd timer that runs it, an apt pin, and the one-time setup that installs them on a machine.

thunar-update, as root in your desktop session you

The big picture

Since #1, every merge into main builds Thunar's three .deb packages and publishes them as a GitHub Release. Until now you still had to download and install them by hand on each machine. This PR adds a small updater that each machine runs by itself: it notices a new release, installs it, and tells you. It never restarts Thunar, so an update can't close your windows.

The updater installs whatever the latest release is, even when it's older than what's installed. So undoing a bad build is just deleting its release on GitHub: within the hour both machines go back to the one before.

Step by step (numbers match the diagram)

① Each machine, 2 min after boot and hourly — check
  1. Timer fires. thunar-update.timer starts thunar-update.service 2 minutes after boot and then on every hour. It is persistent, so an hour missed while the laptop slept runs as soon as it wakes.
  2. Ask GitHub. /usr/local/sbin/thunar-update asks the GitHub API for the latest release of alexhu98/thunar, using the read-only token in /etc/thunar-update/token, which only root can read. If GitHub can't be reached or answers with a server error, it just waits for the next hour; if GitHub rejects the token, you get a notification.
  3. Compare. It downloads only the thunar deb, reads its version from inside the package (dpkg-deb -f … Version) and compares it with the installed one. All three packages must be fully installed at that version, or it counts as different, so a half-finished install is tried again. Same version: it remembers that release and stops, so later hours don't download anything.
  4. Install. When the version differs, it downloads thunar-data and libthunarx-3-0, checks all three have that version, and installs them together with apt-get install --allow-downgrades. A held Thunar is updated too. apt is not asked to repair anything else on the system, so a set it can't finish is reported to you instead.
② After an install — tell you, never restart
  1. Notify you. If Thunar is running, you get “Thunar updated to version; restart Thunar to load it.” in your desktop session. Any failure also sends a notification, pointing to journalctl -u thunar-update: once per failure, and only counted as sent when a session got it, so a failure at boot still reaches you after you log in.
  2. You restart. Thunar keeps running the old build until you close and reopen it, whenever it suits you.

The other pieces

The apt pin

thunar-custom in /etc/apt/preferences.d/ keeps the installed +local build and blocks every other Thunar version from Zorin's repositories, so a system upgrade can't replace it.

The one-time setup

sudo deploy/setup.sh installs the files, asks for the token without showing it, and starts the timer. Run again, it keeps the token unless you pass --new-token.

Undo and recover

A bad build: delete its release on GitHub; the next check installs the previous one. Back to Zorin's Thunar: sudo systemctl disable --now thunar-update.timer, then sudo apt install --allow-downgrades ./*.deb in /mnt/data/Workspace/Thunar-debs/zorin-4.20.2/, and delete /etc/apt/preferences.d/thunar-custom.

Code review

After the first code commit, a fresh general-purpose agent reviewed the diff against the issue at medium level, without running anything. It found 3 problems: 1 high and 2 low. All 3 are fixed, and the mock tests were run again afterwards. CI's own review is in the code review PR comment.

CI's review then found 10 confirmed problems in the fixed code, 4 of them medium or high; all 10 are fixed, and the tests above were run again on the result. The worst: thunar-data is one package for every architecture, so its file ends in _all.deb, and the updater looked only for _amd64.deb and could never have installed anything. The first tests missed it because their stand-in packages were all amd64. The others: a half-finished install counted as up to date; a failure before login was never shown; a missing release was blamed on the token; the token was visible in the process list while curl ran; and setup could stop halfway without a terminal.

Its review of those fixes found 5 more, and CI's bot fixed them: a successful install with Thunar closed ended as a failed service; a rate limit looked like a bad token; apt could repair unrelated packages; a held Thunar was never updated; and a failed temporary folder could leave the token readable. The tests above were run again on the bot's commit.

  • A file missing from the commit (high): the repo ignores every *.service file, so the service unit was never committed and setup would have failed on a fresh checkout. It is now committed explicitly.
  • Misleading message (low): a token without access to the repo gets a 404 from GitHub, not a 401. All three codes now say the token is the problem.
  • Hourly popups (low): an expired token would have shown a new critical notification every hour. Now each failure notifies once, until a check succeeds.

Part 3

What comes later: the rollout on both machines

No open issue builds on this one. What's left is #2's rollout, which only you can do, in this order.

you the updater does it

#2 rollout (next)

  1. Create token. On github.com, a fine-grained token for alexhu98/thunar only, with Contents: read. Note its expiry: when it runs out, the machines notify you that GitHub rejected it, and sudo deploy/setup.sh --new-token replaces it.
  2. Desktop setup. In a checkout of main, run sudo deploy/setup.sh and paste the token. Then sudo systemctl start thunar-update upgrades +local1 to the latest CI build at once, and the notification appears. After restarting Thunar, run the split-view crash check once.
  3. Laptop setup. The same command in a checkout on the laptop. It prompts for the token, so the token is never in a command, a message or the repo.
  4. End to end. Merge a small change; when CI publishes its release, both machines install it within the hour.

Later, #30's upstream watcher will bring each new Xfce release into main, and this updater carries it to both machines with no extra step.

Glossary

.deb
An Ubuntu package file; Thunar ships as three of them.
GitHub Release
A version on the repo's Releases page, with the debs attached; #1's CI publishes one per merge.
systemd timer
Linux's built-in scheduler: it starts a service at set times.
apt pin
A rule that tells apt which version of a package to prefer or refuse.
Fine-grained token
A GitHub password for programs, limited to one repo and one permission, with an expiry date.
+localN
The suffix on this fork's package versions; N goes up with each CI release.
notify-send
The command that shows a desktop notification.
Session bus
Your desktop session's message channel; notifications travel on it.
