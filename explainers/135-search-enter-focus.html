PR #138: Enter in the search box jumps to the results

PR #138, branch 135-search-enter-focus → main, closes #135. After Ctrl+F and a search word, Enter puts the keyboard in the file list, so Down selects the first match, just like Enter, Down in the location bar.

Part 1

What this PR adds

Enter in the search box now moves the focus to the search results and leaves the search as it is. The change is a new branch in thunar/thunar-location-entry.c a small getter in thunar/thunar-window.c and a crash guard in thunar/thunar-path-entry.c, tested by verify/135.sh.

new in this PR existing Thunar behaviour, unchanged you

The big picture

Before, after Ctrl+F and a search word, Enter did nothing and the keyboard stayed in the search box. Down did nothing either: you had to press Tab twice to reach the results. In the location bar, Enter on a folder already moves you into the file list. Now the search box does the same.

Search and the location bar are the same text box. The search runs on every keystroke, so in search mode Enter had nothing left to do. Its only new job is to move the keyboard to the results.

Step by step (numbers match the diagram)

① Enter in the search box
  1. You search. Ctrl+F opens the search box and each letter you type updates the results, as before.
  2. Enter. thunar_location_entry_activate is the box's Enter handler. It finds no file for the text, and now asks thunar_util_is_a_search_query whether the text is a search. When it is, it takes the new branch, whether you came through Ctrl+F or typed “Search: apple” into the location bar yourself (CI's review finding R4).
  3. Keep the bar. Only when thunar_window_is_searching, a new getter in thunar-window.c, says the window is in search mode, the branch disconnects the box's pending “edit done on focus-out” handler. Without that, with the path-buttons style of location bar, moving the focus away would swap the bar back to buttons in the middle of the search. A hand-typed query in a temporary path box keeps the handler, so the box still closes (R1).
  4. Focus to list. In every case it then calls gtk_widget_grab_focus on thunar_window_get_view, the same call the location bar already makes after selecting a file (#93).
② After Enter, and what stays the same
  1. Down: 1st match. With the file list focused and nothing selected, the list's own Down key selects the first match. The search and its results stay on screen.
  2. Path Enter. Enter on a folder or file path takes the old branch, before the new one, so it is unchanged.

The crash guard (thunar-path-entry.c)

/* changed handler: part of "Search: " was deleted */
if (path_entry->search_mode == TRUE)
  {
    window = get_toplevel (editable);
    if (THUNAR_IS_WINDOW (window))
      cancel_search (THUNAR_WINDOW (window));
  }
Why the guard: after Enter on a hand-typed “Search: ” query in a temporary path box (the R4 path), the bar swaps that box for path buttons. The old box, still in search mode but no longer inside the window, had its text set on the next folder change, treated its toplevel as a window, and Thunar crashed. Commit ad4906311 now cancels the search only when the toplevel is a Thunar window.
Not as the issue assumed: the issue says Ctrl+F should bring you back to the search box with the query intact. In Thunar, Ctrl+F while a search is open turns the search off, before and after this PR. Clicking the search box does return to it. You decided to keep Ctrl+F as it is, so there is no follow-up issue (Part 3).

Code review

A local review at high level, of everything on the branch against main, before the first push: 3 findings, none fixed by the review itself, 1 fixed by hand after reading the code.

  • S1, fixed: with the path-buttons bar, Ctrl+L then Ctrl+F left the focus-out handler armed, so Enter would swap the bar back to buttons mid-search. The branch now disconnects it, and the script tests that layout.
  • S2, skipped: no NULL check on the view, a nit. The same file's existing call has none either.
  • S3: the explainer was missing; this page is it.

CI's own review, at high level on e8f80ff, found 3 more, reported in its code review comment on the PR:

  • R1, medium, confirmed, fixed by CI: a hand-typed “Search:” text in a temporary path box would take the new branch and get stuck. CI's commit 21793c3 adds the thunar_window_is_searching check.
  • R2, low, confirmed, accepted by you: the script's buttons-bar part doesn't assert that the text box stays. Shot #55 shows it, and the audit passed it.
  • R3, low, plausible, accepted by you: the location bar's own edit-done handler may stay connected. CI's verifier found no visible effect.

CI's second review, at high level on d9abdac (run 45003563923), found 4 more:

  • R4, medium, confirmed, fixed by CI: R1's search-mode check also gated the focus move, so Enter on a hand-typed “Search:” query left the keyboard in the box. CI's commit 43a5747 moves the focus for any search query and only skips the disconnect when not searching.
  • R5, low, confirmed, accepted by you: a hand-typed “Search:” query filters the list but never turns on search mode, so Escape or deleting the prefix can't cancel it. This is old upstream behaviour; no follow-up issue.
  • R6, low, confirmed, fixed: nothing tested Enter on a hand-typed query. Commit 854321c adds that step to the script, and that step found the crash fixed in ad4906311.
  • R7, low, plausible, accepted under the repo's rule: the first accept commit had its accept line in the wrong paragraph, so an empty commit carried it. No effect on the code; CLAUDE.md accepts later-review low findings that aren't confirmed.

CI's third review, at high level on 28da39b (run 45005553591), resolved R6 and found 3 more:

  • R8, medium, plausible, accepted by you: with the path-buttons bar, Enter on a hand-typed “Search: apple” closes the temporary box and leaves results Escape can't cancel. CI's verifier found it isn't new: Tab, a click or Escape already led there, and changing folder clears it. The root cause is R5.
  • R9, low, plausible, accepted under the repo's rule: the path box's Escape handler treats its toplevel as a window without checking. It's old code, and CI's verifier found only a box inside the window can get the key press.
  • R10, low, confirmed, fixed by CI: the hand-typed step ran only with the path-buttons bar. CI's commit dad4b1c runs it again with the entry-style bar.

CI's fourth review, at high level on cf4b465 (run 45014044062), found 2 more, both in the script:

  • R11, medium, confirmed, fixed by CI: the entry-bar hand-typed step passed even if Enter left the focus in the box, because the step before had left apple1.txt on the clipboard. CI's commit 096cbe9 makes it Ctrl+A, Ctrl+C and expects both apple files.
  • R12, low, confirmed, fixed, then resolved by CI: the hand-typed steps copied only apple1.txt, which is also first in the unfiltered folder, so they couldn't show the view was filtered. Both steps now copy all three files first, then expect exactly the two apple files after Enter, Ctrl+A, Ctrl+C. Focus left in the box or an unfiltered view fails them.

CI's fifth review, at high level on e7d82fc (run 45016506401), resolved R12 and found 3 more, all in the script:

  • R13, low, confirmed, fixed by CI: after Enter, the hand-typed steps sent only Ctrl+A and Ctrl+C, which work anywhere in the window, so they no longer proved the focus reached the view. CI's commit 8a1ea80 adds a round per bar where Enter, Down, Ctrl+C must copy exactly apple1.txt.
  • R14, low, confirmed, fixed by CI: the path-buttons step could pass on the clipboard the step before left behind. The same commit copies all three files first.

Glossary

Focus
The widget that receives your key presses.
Location entry
The text box at the top of the window; it holds a path, or a search after Ctrl+F.
Path-buttons bar
The location bar style that shows the path as buttons and swaps in a text box only while you type.
Edit done
The signal that tells the buttons bar the typing is over, so it swaps back to buttons.
View
The file list: icons, details or compact list.
Xvfb
An invisible X display, used to run Thunar for tests without a screen.
verify script
verify/<issue>.sh: drives Thunar with xdotool, checks the result and takes screenshots.
