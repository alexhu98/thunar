Part 1

What this PR adds

A drop from one pane onto the other no longer moves keyboard focus or the active pane to the drop pane. The whole change is in thunar/thunar-standard-view.c, tested by verify/96.sh.

you changed by this PR unchanged code

The big picture

Split view (F3) shows two folders side by side. One pane is the active one: the location bar, the status bar and the keyboard all follow it. Before this PR, dragging a file from the right pane onto the left one made the left pane active, so the next key (Down, Delete, Ctrl+A) acted on the pane you dropped on, not the one you were working in.

The focus moved twice: once when the drop landed, and again when the move or copy finished. The drop now focuses the source pane when the drag came from the other pane, and the finished job grabs focus only in the window's active pane.

Step by step (numbers match the diagram)

① A drop on the other pane — changed
  1. You drag. You drag a file from the right pane and drop it on the left pane, as in the issue's report.
  2. Drop handler. thunar_standard_view_receive_text_uri_list used to call thunar_window_focus_view on the drop pane. It now asks the new helper thunar_standard_view_is_other_pane first, and when the drag came from the other pane it focuses the source view instead. That also hands focus back when a spring-loaded folder switched panes during the drag.
  3. Move or copy. thunar_dnd_perform starts the job exactly as before, with the same new-files closure.
  4. Job finishes. thunar_standard_view_new_files still selects the dropped files in the left pane, but calls gtk_widget_grab_focus only when that view is the window's active view (thunar_window_get_view), checked when the job ends. It reads the drag's source view through a weak pointer, so a source view closed during a long transfer is never read after it's freed.
② Everything else — unchanged
  1. Other drops. A drop from another app or another window, or within one pane, fails the helper's check, so focus goes to the drop pane as it always did.
  2. Paste, New Folder and rename. These focus the new item through ThunarActionManager's own new-files path, which this PR doesn't touch. Shift+Insert and Ctrl+Insert are Paste and Copy, so they're in this group too.
  3. Insert (#95). “Drop on Other Pane” passes no new-files closure and never moved focus. verify/96.sh now checks that as well.

A closer look at the other-pane check

static gboolean
thunar_standard_view_is_other_pane (ThunarStandardView *standard_view,
                                    GtkWidget          *source_view)
{
  return THUNAR_IS_VIEW (source_view)
         && gtk_widget_get_toplevel (source_view) == gtk_widget_get_toplevel (GTK_WIDGET (standard_view))
         && gtk_widget_get_ancestor (source_view, GTK_TYPE_NOTEBOOK) != gtk_widget_get_ancestor (GTK_WIDGET (standard_view), GTK_TYPE_NOTEBOOK);
}

Same window

The source must be a Thunar view in the same top-level window, so drags from other apps and other Thunar windows don't count.

Different pane

Each pane is its own tab notebook. A different notebook means the other pane; the same one means a drop within one pane.

Tab-label drops (#19)

A drop on the other pane's tab label passes no new-files closure and doesn't switch panes, so it needed no change.

Code review

A fresh general-purpose agent, given only the diff and the issue, found 3 problems. 2 were fixed then; the third, older than this PR, was fixed after CI's review flagged it too.

  • Test too slow (fixed): the drag in verify/96.sh scanned so many rows that it could pass the 120-second test limit. It now starts at the known first-row position, as verify/15.sh does.
  • Spring-loaded folders (fixed): hovering over a folder during the drag could still leave focus in the drop pane. The drop handler now focuses the source view.
  • Older risk (fixed later): the view stored the drag's source view without a weak reference, so a source view closed during a long transfer could be read after it's freed. It is now held through a weak pointer (R4, below).

Glossary

Split view
Two folder panes side by side in one window, toggled with F3.
Active pane
The pane the location bar, status bar and keyboard follow (notebook_selected).
Keyboard focus
The widget that receives key presses; “grabbing focus” moves it there.
Notebook
GTK's tabbed container; each pane is one.
Spring-loaded folder
A folder that opens when you hover over it while dragging.
New-files closure
A callback a drop hands to the job, run with the new files when it finishes.
Insert (#95)
“Drop on Other Pane”: sends the selection to the other pane's folder.
Weak reference
A pointer that is cleared automatically when its object is freed.
Xvfb, xdotool
A screenless X server, and a tool that sends it clicks and keys.
