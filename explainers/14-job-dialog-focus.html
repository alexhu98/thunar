PR #80: File-operation dialogs no longer steal the focus

Branch 14-job-dialog-focus → main, closes #14. Once merged, the progress window and the replace and question dialogs open without taking your keystrokes, and a stray Enter can no longer cancel a copy.

Part 1

What this PR adds

Two changes: the progress window is shown without asking for the focus, and the dialogs a job opens (its questions and its error message) have no default button and open without taking the focus. The code is in thunar-progress-dialog.c, thunar-application.c, thunar-dialogs.c and thunar-progress-view.c.

changed by this PR you

The big picture

During a long copy, Thunar's progress window popped up and took the keyboard away from the app you were typing in. When the copy hit a file that already existed, the replace dialog did the same, and its default button answered the next Enter: in the question dialog that was Cancel, so a stray Enter cancelled the whole copy.

Asking not to be focused is not enough for a modal dialog: xfwm4 focuses a modal dialog when it is mapped, and when its parent is raised, whatever the dialog asks. So the dialog is mapped before it becomes modal, and the progress window is not raised while a dialog of its own is open.

Step by step (numbers match the diagram)

① The progress window
  1. You copy files. You start a copy or move in Thunar and go back to typing in another app.
  2. After 500 ms. If the job is still running, thunar_application_show_progress_dialog_timeout now calls the new thunar_progress_dialog_raise instead of gtk_window_present. A hidden window is shown with gtk_widget_show; the window already asks not to be focused when it appears.
  3. Needs attention. When a job asks a question, the progress window is shown the same way. If it is already visible, it is raised without the focus, unless one of its own dialogs is open: then it is only un-minimized (gdk_window_show_unraised), because raising it made xfwm4 focus that dialog.
② When the job asks a question or fails
  1. No default. thunar_dialogs_show_job_ask no longer makes each button, and last Cancel, the default, and the replace dialog no longer makes Replace the default. The buttons and their order are unchanged. The job error message, which has only Close, now opens through the same code too.
  2. Focus on text. The new thunar_dialogs_run_job_dialog puts the dialog's focus on its message text before it opens. Otherwise GTK would focus the first button, and Enter would press it.
  3. Map, then modal. It asks not to be focused, shows the dialog while it is still not modal and waits for the window manager to put it on screen. Only then does gtk_dialog_run make it modal, so the window manager never sees a new modal window.
  4. You answer. Click the dialog or a button, or Tab to one and press Enter. Escape and closing the dialog still cancel, but only once you have focused it.

Built on 3 known-good references

The window manager spec

A window whose user time is 0 asks not to be focused when it appears; GTK sets that for windows that don't focus on map.

Run under the same xfwm4 as CI, it showed which ways of showing a dialog and its parent move the focus and which don't.

Zorin's Thunar 4.20.2

The packaged Thunar without this PR: the same test was run on it to show it catches the bug.

Code review

A fresh general-purpose agent in this session, given only the diff and issue #14, reviewed it at high effort: no crash or leak, 2 medium and 3 low findings. Both medium findings and one low were fixed; the build and the tests were run again afterwards.

  • Fixed (medium): the wait before making the dialog modal ended at once, because GTK marks a window as shown before the window manager maps it. It now waits for the real map, and closing the parent window can't destroy the dialog during that wait.
  • Fixed (medium): the job error message still took the focus. It now opens through the same code, and verify/14.sh checks it.
  • Fixed (low): the test never showed the progress window without a question; it now copies a 2 GB file first.
  • Kept (low): a progress window that is already open was no longer raised when a job needs attention. CI's review raised it again (R3, below), and that is now fixed.
  • Kept (low): the question the Properties dialog asks when changing permissions of a folder's contents also opens without the focus and without a default button, since it uses the same dialog.

CI's review of 0483279 (level high) reported 10 findings, 1 of them medium. They are in the code review PR comment, the second of CI's comments. The fixes are in the next commit, and the build and verify/14.sh were run again on it.

  • Fixed (medium): the wait for the map still ended after one pass, because Thunar runs no gtk_main loop; it now runs the main context itself (R1).
  • Fixed (low): the job error dialog is titled "Error", and the test finds it by that title (R2, R10). The progress window is raised again when none of its dialogs is open, which a test program showed keeps the focus (R3).
  • Fixed (low): no new doc comment or comments in the test (R7, R8), and the test copies 2 GB instead of 3 (R9).
  • Kept (low): the permissions question follows the same rules, as #14 asks (R4); an input can't arrive while the dialog is not yet on screen (R5); and the focus handling stays in the one shared helper (R6).

Glossary

Keyboard focus
The window, and the widget in it, that receives what you type.
Default button
The dialog button that Enter presses when no other button has the focus.
Modal dialog
A dialog that blocks its parent window until it is answered.
Map
X11's word for putting a window on screen.
User time
A window property; 0 asks the window manager not to focus the window when it appears.
Window manager
The program that places windows and decides which one is focused: xfwm4 in CI, Mutter in GNOME.
xev
A small X program that prints every key it receives; the test types into it as a stand-in for your editor.
Xvfb
A virtual X display with no screen, used to run Thunar in tests.
