PR #70: Fewer CI jobs and fewer comment edits

Branch 56-fewer-jobs → main, closes #56 and #66, refs #58. GitHub bills each job as at least a whole minute, so CI now runs fewer short jobs and edits its PR comments only when they change.

Part 1

What this PR adds

Release folded into verify, review-report run only for a fix, one re-run job dropped, and a skip for unchanged comments. No Thunar code changes.

same as before new in this PR

The big picture

Actions ran out of minutes on 7 November. GitHub rounds every job up to a whole minute, and the short jobs billed 345 minutes for 136 real ones. And every edit of CI's PR comments woke the watching session with the whole comment, even when nothing in it had changed.

A job that runs for 10 seconds bills a full minute. Folding it into a job that already runs saves that minute, as long as the two together stay under the next whole minute.

Step by step (numbers match the diagram)

① On a PR
  1. Review reports. Most reviews leave no fix to push: they found nothing to fix, ran in suggest mode, or were skipped. Then the review job's last step, from a fresh checkout of the head, posts the suggestions and writes the review comment itself, without the push token. Only a review that left a fix, or one whose own report didn't write the review comment, starts review-report, on a fresh machine with the token, as before. The model never shares a machine with the token: it could have left files or a running process behind.
  2. Same body? pr-comment.sh put reads the comment first and skips the edit when the new body is identical, link for link. Most of the summary's rewrites, such as the summary job's final one, no longer reach the watching session.
  3. Audit posted. A /visual-verify comment used to make pr-summary.yml re-run the build run's summary job, a second billed job. It now runs pr-summary.py itself, from main's scripts, once the head's build run has finished.
  4. Same checks. A PR still shows build, verify, explainer, review, review-report and summary, with the changes step, the No code changed steps and ccache as before. review-report is now skipped when there is no fix, so the merge rule in CLAUDE.md allows that.
② On a push to main
  1. Build. Unchanged: on a push, build stamps the release version and builds the debs, with ccache.
  2. Verify. Unchanged: verify installs those debs and runs the smoke test and every verify/<issue>.sh.
  3. Release in verify. The release job's two steps, publish and keep the newest 10, now run at the end of verify on a push. verify already had write access to the repo's contents and the debs in dist/, so no job gains access, and build stays read-only.
  4. Only if verified. The old release job needed only build. Now a push whose tests fail publishes no release, so a broken build no longer reaches the releases page.

Why #58 is left out

The idea

Stamp PR builds with the next release version, so a push could release the merged PR's debs instead of rebuilding.

The catch

Every open PR's debs would then carry that same version with different contents. A PR deb installed for testing would stop the real release from installing.

The other way

Re-stamping the PR's debs at release time means rewriting their control files, changelog and checksums, then releasing them untested. Not clean, so #58 stays open.

Already writes the summary from any job; pr-summary.yml now calls it the same way.

Code review

A fresh agent, given the diff and the intent, found 7 in the first version: 2 high, 1 medium, 4 low. Both highs and one low are fixed. The medium, the merge rule's job names, went to the owner, who approved the CLAUDE.md edit. Kept on purpose: an audit no longer re-runs a failed summary check, though it still updates the comment.

  • The push token beside the model: the first version ran the whole report on the review's machine. The model can write files there, such as a Python module or a git config the report would load, or leave a process running. Fixed by keeping review-report on its own machine whenever there is a fix to push.
  • A fork's ccache into a release: reused debs could carry objects a fork PR's earlier push left in its ccache. Fixed at first by reusing only this repo's runs, then moot once #58 was left out.

CI's first review, at high in 6 minutes, found 9: 3 medium, 6 low, R1–R9. Fixed in one push: build no longer gets write access, because the release moved into verify (R1); PR debs no longer carry the next release's version, because #58 is left out (R2, and R8 with it); the in-job report calls the script directly (R6); the job's minutes are computed without a round trip (R7); and the unchanged-comment check reads the bodies from the list it already fetched (R9). R3, R4 and R5 wait on the owner: the CLAUDE.md edit, the report sharing the review job's time limit, and the review job's PR-write token, which #56 listed as a known cost.

CI's second review, in 4 minutes, found R1 and R2 resolved and 6 more, R10–R15. R10, a confirmed medium: the in-job report ran scripts from the tree the auto-fix model may have edited. Fixed in one push with R6, R9, R14 and R15: the report runs from a fresh checkout of the head, both report steps just call review-proof.sh report, and pr-comment.sh get reads the body from its list. R11 and R12, two lows its own check disproved, and R13, a low about re-running a failed verify after a newer release (the old release job behaved the same), are accepted.

CI's third review passed, with R10 resolved and 5 more, R16–R20. Fixed in one push: the report step now waits for its checkout (R16), pr-comment.sh get reads the whole list so the pipe can't break (R17), and the self-copy is gone, since a fix can never touch .github/scripts/ (R18). R19, the extra checkout's cost, is accepted. R20, the report reading files the model could write, is with the owner: review-report read the same files before, from the uploaded artifact.

CI's fourth review passed, with R6 and R9 resolved and R16 still open: when the fresh checkout fails, neither report ran. Now review-report also runs whenever the in-job report didn't (R16). R21, a low about a planted Python module, which the review itself found no route for, is accepted.

CI's fifth review found that fallback still wrong, R22–R28: it lost a finished review's findings when the checkout failed, and missed a report that stopped early. One output now hands over: the report sets reported once it has written the review comment, review-report runs whenever that isn't set, and it gets the review's own result, recorded before the report checkout. R27, an edit not in the PR, is accepted.

CI's sixth review found 3 more about that hand-over, all fixed: a report that stops before writing the comment no longer turns the review check red, since review-report reports instead (R29); a suggested output keeps the suggestions from being posted twice (R30); and a dry run sets neither output (R31).

CI's seventh review passed with 7 lows. The 3 confirmed ones and one more are fixed: suggested is set only once suggestions were posted (R32, R34), a failed report checkout prints its warning (R33), and the report clears its marker when it starts (R37). R35 (the merge rule, with the owner), R36 and R38 are accepted.

CI's eighth review passed with 4 lows. Holding suggested back after a partial post would make review-report post the whole batch again (R39), so it is now set once posting was tried, and the IDs that failed travel in suggest_failed. The dead marker cleanup is gone (R40) and the header says what the output means (R41). R42, the extra warning step, is accepted.

CI's ninth review passed with 3 lows, none confirmed, all about the same suggestions hand-over in the rare case the in-job report fails between posting and writing the comment: R43, R44 and R45 are accepted, which ends the rounds.

The owner decided the rest: the CLAUDE.md merge rule now allows review-report to be skipped when the review reported itself (R3), and R4, R5 and R20, the costs of the in-job report, are accepted.

Glossary

Billed minute
GitHub charges each job's run time rounded up to a whole minute.
Job
One part of a workflow run on its own fresh machine, shown as one check on the PR.
Step
One command or action inside a job; steps share the job's machine.
Artifact
Files a run keeps for 14 days, such as the built .deb packages.
Push token
The secret that lets CI's review push its fix commit to the PR branch.
