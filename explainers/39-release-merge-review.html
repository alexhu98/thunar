PR #46: CI reviews an upstream release merge by the fork's own changes

Branch 39-release-merge-review → main, closes #39. Once merged, a PR that merges a new Thunar release gets suggested changes on the fork's own work only, instead of a review of upstream's whole release, and the watcher skill needs no trailer tricks.

Part 1

What this PR adds

CI's review planner, .github/scripts/review-proof.sh, now spots a release merge and plans its review differently. The upstream watcher's skill drops the rules that worked around the old behaviour.

review-proof.sh the upstream-merge skill

The big picture

Every week a skill checks for a new Thunar release and opens a PR that merges it into main. CI reviews every PR, but its review compared the branch with the point where it left main. For a release merge that means every upstream commit in the release, so the review flagged upstream's code, and in its default mode it would even commit edits to it.

What the fork actually decides in a release merge is small: how each conflict was resolved, and anything committed after the merge. Git can show the first exactly: git show --remerge-diff compares the merge with the merge git would have made on its own.

Step by step (numbers match the diagram)

① Plan, every push to a PR
  1. Find the merge. review-proof.sh plan looks along the branch's own line of commits for a merge titled Merge upstream thunar-<version> whose second parent, the release tag, is not already on main. The branch name plays no part, so a normal PR can't be mistaken for one.
  2. Suggest mode. With no Review: trailer on the head commit, a release PR gets suggested changes instead of a fix commit. An explicit trailer still wins.
  3. Skip idle pushes. A push that changes only explainers/, or nothing, since the last review is skipped, even if its head carries Review: suggest. So is a release PR whose own side is empty, such as a clean merge plus its explainer, unless findings from an earlier review are still open: then the review runs only to re-check them.
  4. The fork's side. The review's diff.patch holds git show --remerge-diff of the merge and git diff from the merge to the head. If the branch has other commits around the merge, such as a later merge of main, it is instead the diff from git's own merge of the release (git merge-tree) to the head. The prompt tells the reviewer that upstream's release is not under review.
② Report, and the watcher
  1. Comments placed. hunks() lists where inline suggestions may go. For a release PR it keeps only lines that are both in the PR's diff on GitHub and in the fork's side, found by diffing git's own automatic merge (git merge-tree) against the head.
  2. Simpler skill. .claude/skills/upstream-merge/SKILL.md no longer ends every push with a Review: suggest commit or closes findings in upstream's code with Review-accept. It only asks to keep the merge's title, which is how CI finds it.

Code review

After the first code commit, a fresh agent given only the diff and issue #39 reviewed it, running its functions on a scratch repo: 2 medium and 4 low findings. Both mediums were fixed, and every test above was re-run after the fix.

  • main merged in later (fixed): the fork's diff then showed other PRs' code twice, once reversed. It now uses git's own merge of the release in that case, as the comment positions already did.
  • How the review skill reads a path (fixed): it might have reviewed the patch file as a file. Its arguments now say it is a diff whose changes are reported at their lines at HEAD.
  • Low, left as is: a failed diff inside the comment-line list goes unreported; a shallow clone could misdetect a merge (CI fetches full history); context lines next to a resolution can take comments; very large diffs may refuse inline comments.

Glossary

Release merge
A commit that merges an upstream Thunar release tag into the fork.
Remerge diff
The difference between a merge as committed and the merge git would make by itself.
Review: trailer
A last line in a commit message that picks CI's review mode.
Review-accept
A trailer that closes CI findings kept on purpose.
Suggest mode
CI posts suggested changes on the PR instead of pushing a fix commit.
Hunk
One block of changed lines in a diff; inline comments must sit inside one.
First-parent line
The branch's own commits, not the ones a merge brought in.
