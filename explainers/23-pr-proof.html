Part 1

What this PR adds

CI now writes four PR comments instead of one: summary, code review, verify and explainer. The verify job numbers every shot and turns each before/after pair into one 1920 px image, and every job refreshes the summary when it finishes.

the verify job every job that writes a comment you

The big picture

Every PR gets proof from CI: the build, screenshots of the feature, an independent code review and a rendered explainer. Until now all of it went into one comment. On PR #20 that comment was about 20,000 pixels tall, the explainer came first, before and after shots were a screen apart, and nothing near a pair said what the test did between them. This PR splits the proof into four comments in the order a reviewer decides, and shows each pair as one image with its story right above it.

Each comment is found by a marker on its first line, such as <!-- pr-proof:verify -->, and carries a hidden status line. The summary is built only from those status lines, the build job's result and the latest screenshot audit, so any job can rewrite it.

Step by step (numbers match the diagram)

① Verify job
  1. Describe pairs. After its before-<what> and after-<what> shots, a verify script calls pair <what> "ACTION" "PROVES" "BEFORE-STATE" "AFTER-STATE" [GROUP] from verify-lib.sh, which adds a row to pairs.tsv. A test that passes with a pair and no pair call is marked "pairs incomplete" and fails.
  2. Number, compose. verify-shots.py build numbers the shots in the order they were saved, verify scripts first and the smoke test last, a pair being one number. It writes the manifest with a new num column, and makes each pair one 1920 px image with ImageMagick: before on the left with a blue "#6 BEFORE" bar, after on the right with a green "#6 AFTER" bar.
  3. Upload, post. verify-proof.sh publish commits the original shots, the pair images and the manifest to the shots branch, then writes the verify comment: the results table, then every shot except the key result, grouped under the script's headings.
  4. You review. The summary says whether the PR is ready and which check failed first. Nothing in any comment is behind a click.
② Every job
  1. Four comments. The first time any job writes, pr-comment.sh put creates all four placeholders in the order summary, review, verify, explainer, then edits its own. When two jobs create them at once, each name keeps its oldest comment, which keeps the order, and the newer duplicates are deleted.
  2. Summary. After writing its comment, each job runs pr-summary.py. It reads the status lines, the build job and the latest /visual-verify verdict posted for the head, and writes the heading, the checks table, the key pair and the shots table. It does nothing when a newer commit has been pushed.
  3. Summary job. A new summary job runs after every other job, even when one failed, and writes the summary one last time. It also covers a failed build, after which the verify job never runs.

Code review

A fresh general-purpose agent, given only the diff and the issue, reviewed the change and checked each finding against the code: 1 high, 3 medium and 5 low. All 9 were fixed, and the tests above were run again after the fixes.

  • Comment size: keeping every finding whole would pass GitHub's 65,536-character limit after about 45 findings. Closed findings now keep a short text, and the comment shortens them further, then drops the oldest rows, to stay under 60,000.
  • Runs cut short: a run that timed out published no shots. publish now numbers the shots itself when run didn't, and a missing numbering fails the Verify row.
  • Summary freshness: a failed build now writes the summary from the build job itself, and each writer reads everything again after writing and rewrites once if a result or the head changed.
  • Smaller fixes: only the owner and collaborators can post an audit verdict; the review state in the old single comment is carried over once and that comment deleted; one failed pair image no longer spoils the rest; a shot with no group gets its own heading; the explainer comment no longer stops early when there is no narration result.

CI's own review of the PR goes in the code review comment, the second of the four.

Glossary

Pair
Two shots of the same window, before-<what> and after-<what>, around one action.
Key result
The first pair of the issue's own verify script, shown in the summary.
Marker
An invisible HTML comment on a comment's first line that tells CI which of the four it is.
Status line
A hidden line in a comment giving its commit, pass or fail, and a short result.
shots branch
A branch with no code that holds every PR's screenshots, so comments can link to them.
Manifest
verify.tsv: one row per shot with its number, test, file and what it proves.
Xvfb
A virtual screen with no monitor, where CI runs Thunar.
Screenshot audit
/visual-verify: an independent agent checks that each shot shows what it claims.
