What this PR adds

you command handling, thunar-application.c the new window

The big picture

Until now Thunar always opened its windows at the last size you used, on the workspace you were looking at. To set up a work layout from a script, as Nemo's -g allows, you need to say where the window goes. This PR adds that for one new window per command, and leaves your remembered window size alone.

The thunar you type usually just hands its options to a Thunar that is already running. So the options have to travel with the command, and be applied only at the moment that Thunar creates a new window.

Step by step (numbers match the diagram)

① Your command reaches Thunar
  1. You run thunar. -g WxH+X+Y (or --geometry=) sets the size and place; -s N (or --workspace=N) picks the workspace, counting from 1 as Xfce names them. Both work with -w, -t and -T.
  2. Values kept. In your own process, thunar_application_local_command_line passes the option values on untouched. Without this, a value after -T would be taken as a right-pane folder. It also counts each g and s in a group like -gs.
  3. Parsed once. thunar_application_command_line, in the running Thunar, reads WxH, +X+Y, WxH+X+Y and negative offsets, and a workspace from 1 to the number of workspaces. Numbers must fit X's 16-bit range, and a display with no workspaces rejects -s. A bad value prints Thunar: invalid geometry "…" or invalid workspace "…", and the window opens as usual.
  4. With the 1st file. The parsed options join a queue, window_options_to_launch, that runs alongside the files waiting to open, or go with the -t/-T set of tabs. They are handed to the window code as a parameter, so they belong to this one command: not to a window from Ctrl+N, nor to another command for the same folder.
② The new window gets them
  1. New window only. thunar_application_open_window_full applies the options only when it creates a window; the public thunar_application_open_window passes none. If the folder opens as a tab in a window you already have, they are ignored, as the issues ask.
  2. Size and place. The window is un-maximized first, even for a place only, so a remembered maximized state can't override -g. The size goes in with gtk_window_set_default_size. The place uses a gravity and gtk_window_move, so -40-40 means 40 pixels from the right and bottom edges. Placing works on X11; on Wayland only the size applies.
  3. Workspace at map. Just before a window first appears, GTK deletes its workspace property. So a one-shot handler sets _NET_WM_DESKTOP as the window is mapped, in the same batch of X requests. xfwm4 puts it straight on that workspace, and your view doesn't move. In case a window manager read the property first, it also sends gdk_x11_window_move_to_desktop.
  4. Size not saved. Thunar saves its window size a second after each resize. thunar_window_keep_size_unsaved skips that save while the window keeps the size -g gave it, or the size the window manager settled on at the first save within 5 seconds. After that first save, any resize by hand is saved as before.

One change from the issue's plan

The issue suggested

gdk_x11_window_move_to_desktop after realizing the window. It only sends a message to the window manager, and xfwm4 ignores that for a window that isn't on screen yet.

What the PR does

Sets the _NET_WM_DESKTOP property itself from a map handler, after GTK has cleared it, so the window manager reads it as the window appears. The suggested call follows as a fallback.

Code review

A fresh general-purpose agent, at level high, given only the diff and the two issues, found 5 things. 4 were fixed before the test run above; 1 was kept.

  • Workspace (high): GTK deletes _NET_WM_DESKTOP just before showing the window, so setting it earlier did nothing. It's now set from a map handler.
  • Saved size (medium): if the window manager shrank the window to fit, that size would have been saved as the remembered one. The size it settles on at the first save now counts as the -g size too.
  • Leak to another window (low): options held on Thunar itself could reach a window opened before the first file finished opening. They then rode on the file; after CI's review they wait in a queue.
  • Grouped flags (low): -gs after -T lost its values. Each g and s in a group now takes one value.
  • Kept (low): negative offsets are worked out from the default size, not the final one, the same as gtk_window_parse_geometry.

CI's own review, at level high, of commit 96309afbc (run 43156400985) found 10 things, R1 to R10. CI's commit 1264eb2 fixed 5, commit 886ee71 fixed 4, and 1 was kept. They are listed in the code review comment on PR #102.

  • Fixed by CI (R1, R4, R5, R6, R7): -g with only a place now un-maximizes too; a display with no workspaces no longer trips a GLib check; numbers are limited to X's 16-bit range; the test waits before measuring +20+30; comments removed from the test.
  • Resize swallowed (R2, medium): for 5 seconds after a -g open, a resize by hand wasn't saved. The grace now ends at the first save.
  • Options swapped (R3, low): they sat on the file object, which Thunar shares, so two commands for one folder could swap them. They now wait in their own queue.
  • Hidden hand-off (R10, low): options reached the window code through fields on Thunar itself. Two private _full functions now take them as a parameter.
  • Workspace fallback (R8, low): after setting the property at map, it also sends gdk_x11_window_move_to_desktop, in case the window manager read the property first.
  • Kept (R9, low): -g and -s are ignored when a setting turns the open into a tab. Issues #5 and #6 ask for exactly that.

The fixes in 886ee71 have no results yet: the local build and test is running, and CI reviews and tests the push again.

Glossary

Geometry
X11's way to write a window's size and place: WxH+X+Y, in pixels.
Negative offset
-X-Y: distance from the screen's right and bottom edges instead of left and top.
Workspace
One of Xfce's virtual desktops; you switch between them, each with its own windows.
X11
The classic Linux display system Xfce runs on; programs may place their own windows.
Wayland
The newer display system; programs can't choose where their windows go.
xfwm4
Xfce's window manager: it draws window frames and decides where windows go.
_NET_WM_DESKTOP
The window property that tells the window manager which workspace a window is on.
Map
X11's word for a window first being put on screen.
Gravity
Which corner of the window a position refers to, e.g. bottom-right for -X-Y.
Frame
The title bar and border the window manager adds around a window.
GOption
GLib's command-line option parser; its entries also reach an already running Thunar.
Launch queue
The list of files a command asked to open; the options now wait in a matching list beside it.
xfconf
Xfce's settings store; /last-window-width is where Thunar remembers its size.
xdotool
A tool that drives and reads X11 windows; the test uses it.
Pair
A before and after screenshot around one action in a test.
